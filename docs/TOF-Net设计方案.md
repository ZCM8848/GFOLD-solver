# TOF-Net：基于神经网络飞行时间预测的高频 MPC 制导方案

> 目标：为 G-FOLD（Fuel-Optimal Large Divert Guidance）求解器外挂一个学习型 TOF（Time-of-Flight）预测器，跳过求解器内部的 TF 搜索，实现 60Hz+ 的高频 MPC 动力下降制导。

## 1. 总体思路

G-FOLD 求解器默认模式下需要内部搜索燃料最优的飞行时间，这是在线求解的主要耗时来源。方案核心：

- **离线**：大规模蒙特卡洛采样 + 并行求解，生成「状态/约束 → 最优 TF」数据集
- **训练**：多任务 MLP 学习可行性分类 + TF 回归
- **在线**：kRPC 读火箭实时状态 → 网络预测 TF → 固定 TF 调用求解器 → 执行轨迹首段控制 → 高频重算

该方法在学术上对应 *learned TF prediction / neural warm-start*，已被动力下降制导文献验证。且固定 TF 求解对 TF 误差有容忍度——预测略有偏差只略多耗燃料，轨迹仍可行且接近最优。

## 2. 数据生成（离线管线）

### 2.1 采样空间

| 输入量 | 说明 |
|---|---|
| 初始位置 (x, y, z) | 相对目标着陆点 |
| 初始速度 (vx, vy, vz) | 含垂直/水平分量 |
| 初始质量 m | 反映剩余燃料 |
| 任务约束 | 目标点、推力上下限、glide slope 角等 |

### 2.2 采样与标注

- 全 CPU 并行蒙特卡洛，目标数十万样本
- 每条样本以求解器完整 TF 搜索模式求解，记录：
  - 可行性标签（求解成功/失败）
  - 最优 TF（仅可行样本）
  - 燃料消耗、求解耗时（备用，供后续 warm-start 升级）
  - ~~不可行样本的违反类型/程度（如燃料缺口）~~ **（deferred：gfold 为黑盒 API，仅抛 ValueError 消息、无结构化违反信息，需额外探测求解才能量化）**
- **采样分布匹配实际飞行包线**：先粗采样，再在典型任务走廊附近加密，避免模型在实际使用区域精度不足

> 实现状态：可行性标签、最优 TF、燃料、耗时均已落地（见 `data/shard_*.npz` 与 `logs/samples.jsonl`）。违反类型/程度未实现。

## 3. 网络设计：单模型双头（Multi-task MLP）

**不需要两个独立 .pt。** 一个共享 backbone，分两个输出头——「可不可行」和「飞多久」依赖同一批物理特征，共享底层表示对两个任务都有益。

```
输入（状态 + 约束，归一化）
   │
 共享 MLP backbone
   ├── 分类头：可行性概率 p（sigmoid）
   └── 回归头：TF 预测值
```

### 3.1 损失函数

```
L = λ1 · BCE(可行性) + λ2 · MSE(TF) · feasibility_mask
```

**关键：TF 回归损失只在可行样本上计算**——不可行样本没有「最优 TF」标签。

### 3.2 为什么不用单头 + 哨兵值

把不可行样本 TF 标 0/-1 也能 work，但回归头在可行性边界附近会输出模糊中间值，阈值难定。显式双头更干净、更稳。

## 4. 在线推理逻辑

```python
p_feasible, tf_pred = model(state)

if p_feasible < threshold:           # 阈值不按默认 0.5，按验证集 PR 曲线选
    fallback()                        # 完整 TF 搜索 / 中止 / 重定向
else:
    solve_with_fixed_tf(tf_pred)      # 固定 TOF 求解；失败同样 fallback
```

### 4.1 阈值按代价非对称调整

- 误报「可行」的代价：求解器失败、浪费一帧
- 误报「不可行」的代价：错过本可挽救的窗口

用验证集 PR 曲线选阈值，不要默认 0.5。

### 4.2 必备 fallback

模型可能对不可行状态输出 TF，导致求解失败。在线必须加「求解失败 → 回退到完整 TF 搜索」的兜底；目标是将预测 TF 固定求解的成功率做到接近 100%。

## 5. 实时性核算

瓶颈不在 MLP（前向为微秒级），而在固定 TF 的那次 SOCP 求解：

- Clarabel 求解通常为几毫秒~几十毫秒，取决于 horizon 长度
- 60Hz 意味着每次求解预算 16ms，可能需要：
  - 减小离散化步数
  - Warm start：以上一帧的解作为初始点
- **先实测固定 TF 模式的单次求解耗时分布，再定 MPC 频率**

## 6. 工程实现要点

- kRPC 为 Python 环境，可直接 `import torch` 加载 .pt
- **模型常驻内存**：torch 加载开销大，进程常驻，切勿每帧重新加载
- 求解器有 Python binding（`pip install gfold`），整条链路可全在 Python 内完成
- 求解器调用：设置 `time_of_flight = tf_pred` 即跳过内部搜索（对应 `gfold.solve(cfg)`）

## 8. 后续升级方向

1. **软着陆降级**：利用不可行样本的违反程度标签，预测「离可行还差多少」，对接 Blackmore 等人的 minimum-landing-error 思路
